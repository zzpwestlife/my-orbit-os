# Claude Code 缓存机制深度解析

## 核心发现

同一段对话，Gemma 4 的 prompt 处理时间从 31 秒直降到 0.25 秒 —— **100 倍加速**。加速只发生在"消化输入"阶段，和"吐出回答"无关。

## KV 缓存原理

### 注意力机制的 QKV

```
Attention(Q, K, V) = softmax(Q · Kᵀ / √d) · V
```

- **Q (Query)**：当前新 token 的"我要找什么？"→ 每次不同，不能缓存
- **K (Key)**：历史 token 的"我这有什么？"（索引）→ 算完就固定，可以缓存
- **V (Value)**：历史 token 的"具体内容是什么？"→ 算完就固定，可以缓存

**KV 缓存就是把历史 token 的 Key 和 Value 存起来，新 token 只需要算自己的 Q，然后查已有的 KV。**

### 为什么可行：Decoder-only 架构

当前所有主流大模型（Claude、GPT、Gemini、Llama、Gemma、Qwen）都是 **Decoder-only** 架构 —— 单向注意力，每个 token 只看前面的 token。前面 token 的 KV 算完就固定了，后面怎么追加都不影响。

```
因果掩码（causal mask）：
   T₁   T₂  T₃  T₄
T₁ ✅ ❌ ❌ ❌
T₂ ✅ ✅ ❌ ❌
T₃ ✅ ✅ ✅ ❌ ← T₃ 的 KV 永远不变
T₄ ✅ ✅ ✅ ✅ ← 新增 T₄ 不影响 T₁₂₃
```

## 模型越大，缓存收益越大

| 模型 | 未命中 | 命中 | 加速比 | 命中时速度 |
|------|--------|------|--------|------------|
| Gemma 4 (4.5B active) | ~25,000ms | ~170ms | 148x | 3,000-5,000 tok/s |
| Qwen3.5 (0.8B) | ~566ms | ~173ms | 3.3x | 3,200-3,900 tok/s |

命中时两个模型速度几乎一样，都是从内存读取。

## 缓存是无损的吗？

**无损**。Transformer 的计算是确定性的，KV 从缓存加载和现场计算的结果完全一致。

**生成结果不进 prompt 缓存**。但在下一轮对话中，上轮的生成结果被拼回 prompt，变成了"输入"的一部分，自然被缓存覆盖。

## 多轮对话的上下文累计

假设：系统提示 20K tokens，每轮对话增加 ~1K tokens

**没有缓存（每轮全价）**：
- 10 轮总计：~255K tokens（全价）← 二次增长，越来越贵

**有缓存（前缀 1/10 价格）**：
- 10 轮总计：~60K 等价 tokens ← 近似线性增长

**对比：255K vs 60K，缓存省了 76%。**

## Claude Code 的缓存工程

### Prompt 的多层结构

```
┌────────────────────────────────────────────────┐
│ system（系统提示词，~20K tokens）                 │
│   Block 1: 计费归因头              → 不缓存       │
│   Block 2: CLI 前缀               → 不缓存       │
│   Block 3: 静态指令（行为规则等）   → global 缓存   │ ← 全球所有用户共享！
│   ──── DYNAMIC_BOUNDARY ────                    │
│   Block 4: 动态内容（CLAUDE.md 等） → org 缓存     │
├─────────────────────────────────────────────────┤
│ tools（工具 schema，session 内冻结）               │
├─────────────────────────────────────────────────｜
│ messages（对话历史）                              │
│   最后一条消息上放 cache_control 标记               │
└─────────────────────────────────────────────────┘
```

缓存是**前缀匹配**的：只要从头开始的 token 序列一致，就能复用。

### 两档 TTL

- **默认 5 分钟** — 所有用户
- **扩展 1 小时** — Pro / Max 订阅用户（未超额）、Anthropic 员工

### 缓存断裂检测

Claude Code 会监控每次调用的 `cache_read_input_tokens`，如果比上次下降 **>5%** 且绝对值 **>2000 tokens**，判定为断裂，并分析原因。

## 缓存像链条：断在哪里，后面全废

```
最贵：Block 3（全局静态）失效 → 整个请求从头算
      [❌ Block3] [❌ Block4] [❌ msg1] [❌ msg2] [❌ msg3]

中等：Block 4（CLAUDE.md）变了 → Block 3 还能复用
      [✅ Block3] [❌ Block4] [❌ msg1] [❌ msg2] [❌ msg3]

最省：只追加新消息 → 前面全部复用
      [✅ Block3] [✅ Block4] [✅ msg1] [✅ msg2] [新 msg3]
```

**切换模型**也是完全失效 —— Opus 和 Sonnet 的权重不同，KV 张量不能互用。

## Sub-agent 能复用主线程的缓存吗？

**答案：几乎不能。**

每个 sub-agent 是一次独立的 API 调用，有三个关键不同：
1. **工具集不同** — 工具 schema 不同 → 缓存前缀不同
2. **消息历史完全独立** — 和主线程的历史没有交集
3. **可能用不同模型** — 不同模型 = 不同权重 = KV 张量完全不同

## 保护你的缓存：使用姿势

### 保护缓存的（绿灯）

- **连续对话** — 前缀不变，增量缓存
- **btw** — 使用 btw 共享 session，可共享缓存
- **CLAUDE.md** — 定期整理，但不要在工作到一半时整理

### 破坏缓存的（红灯）

- **开新 session** — 冷缓存，~20K tokens 全价重算
- **改 CLAUDE.md** — Block 4 起全部失效
- **加减 MCP 工具** — 工具 schema 变化 = 缓存断裂
- **切换模型** — 完全失效
- **/compact** — 消息历史变了 = 断裂
- **发呆超过 TTL** — 缓存过期

### 缓存差异有多大？

假设系统提示词 20K tokens，对话 10 轮：
- 一个 session 持续对话：1 次全价 + 9 次 1/10 = **1.9 份**
- 每次开新 session：10 次全价 = **10 份**

差了 **5 倍**。

## 进阶想法：Cache Keep-Alive 续命

Pro / Max 用户的 TTL 是 1 小时。可以用 tmux 或 iTerm2 AppleScript，每 55 分钟往 Claude Code 终端自动发一条 prompt 来刷新缓存。

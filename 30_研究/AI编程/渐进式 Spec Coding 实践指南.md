# 渐进式 Spec Coding 实践指南

## 核心理念

**Spec Coding**：在让 AI 写代码之前，先用结构化文档（Spec）把"要做什么、怎么做、有什么约束"说清楚，然后 AI 围绕这份文档编码。

## 三大基础认知

### 1. 模型能力的断崖式差异

- **T0 模型**（Claude Opus 4.6、Gemini 3.1 Pro）：一次生成全链路且主动处理边界情况
- **T1 模型**：多提示一两轮可达到接近效果
- **T1.5 模型**：基本可用但容易漏边界
- **T2 模型**：能写骨架但需要较多人工调整

**核心结论**：模型是地基，方法论是上层建筑。地基不行，上面盖得再好也白搭。

### 2. Agent = while 循环 + Tool Use + 工具执行器

工具的边界就是 Agent 的能力边界。安全靠框架约束，不靠 AI 自觉。

### 3. 软件复杂度视角

- **本质复杂度**：业务逻辑本身，不可消除
- **偶然复杂度**：工具/流程引入的额外负担，可以且应该被消除

**评判标准**：一个方案好不好，看它能多高效地帮你应对本质复杂度，同时自身引入的偶然复杂度有多低。

## Vibe Coding 的四大工程问题

| 问题 | 表现 |
|------|------|
| 上下文丢失 | AI 不知道项目历史，每次从零开始 |
| 需求漂移 | 多轮对话后偏离原始目标 |
| 质量不可控 | 同样的需求，不同人得到的代码质量差异巨大 |
| 无法复现 | 对话记录丢失后，决策过程无法追溯 |

## Spec Coding 三条铁律

1. **No Spec, No Code** — 没有文档，不准写代码
2. **Spec is Truth** — 文档和代码冲突时，错的一定是代码
3. **Reverse Sync** — 发现 Bug，先修文档，再修代码

## 经济学原理：Code is Cheap, Context is Expensive

把需求、约束、代码现状写进 Spec 作为高质量输入 → 输入增加但便宜 → AI 不用反复试错 → 输出大幅减少 → 对话轮次从 20 轮降到 3-5 轮 → 总成本反而更低，效果反而更好。

## 渐进式复杂度设计

**核心思想**：不同复杂度的需求，暴露不同深度的流程。

| 复杂度 | 流程 | 适用场景 |
|--------|------|----------|
| 🟢 简单 | Rules only | 改字段、修 bug（≤1 人日） |
| 🟡 中等 | Rules + Spec | 新增功能、重构模块（2-5 人日） |
| 🔴 复杂 | Rules + Spec + Tasks | 跨模块变更、架构调整（>5 人日） |

**关键原则**：简单需求不承担复杂流程的成本。

## 工作流：Propose → Apply → Review → Archive

### Propose（提案）— 人主导，AI 辅助

1. **Research**：分析代码现状，锁定事实（每个结论有代码出处）
2. **逐个提问**：一次只问一个问题，优先给 2-3 个选项 + 推荐
3. **YAGNI 裁剪**：主动识别"nice to have"建议延后
4. **分段生成文档**：按段输出并确认，越早发现偏差修正成本越低
5. **HARD-GATE 确认**：完整 spec + tasks 生成后，必须等用户显式确认

### Apply（执行）— AI 主导，人审查

- **默认逐步执行**：完成一个 task → 报告 → 等用户确认
- **零偏差原则**：Plan 是合同，AI 是打印机
- **Verification 铁律**：每个 task 完成后必须展示可验证的证据
- **实时知识采集**：每个 task 完成后立即检查是否踩坑/发现隐含规则

### Review（审查）— 两阶段 Sub Agent 审查

1. **Spec Compliance**（spec-reviewer）：逐条比对 spec 功能点与实际代码
2. **Code Quality**（code-quality-reviewer）：检查编码规范、安全红线、异常处理

阶段一 PASS 后才启动阶段二。

### Archive（归档）— 知识沉淀

逐条展示 log.md 中的知识发现和踩坑记录，询问用户是否沉淀到 knowledge/。

## 工具选型：编排层 + 执行层

```
人（开发者）
  │
  ├─ 对话界面
  │       │
  │       ▼
  │   编排层 AI（强模型，如 Claude Opus）
  │   职责: 理解需求、生成 Spec、审查结果
  │       │
  │       ▼
  │   执行层 AI（编码工具，如 Claude Code / opencode）
  │   职责: 读写代码、执行命令、运行测试
  │
  └─ 终端 — 可随时直接接管编码工具
```

**透明度底线**：模型型号 + 版本可见、完整 context 可查、原始输出不被篡改、token 用量透明。

## 人的角色：管控、指挥、评价

| 阶段 | 自由度 | 为什么 |
|------|--------|--------|
| 调研 | 中 | 让 AI 自由探索，但必须给证据 |
| 方案设计 | 高 | 唯一鼓励 AI 充分想象的阶段 |
| 规划 | 低 | 精确到文件路径和函数签名 |
| 执行 | 零 | 严格按计划施工，有问题必须停下来问 |
| 验收 | 中 | 自由检查，但结论要有依据 |

## 知识底座才是真正的护城河

| 知识类型 | Spec 能覆盖 | 实际重要性 |
|----------|-------------|------------|
| 编码规范 | ★★★★ | ★★★ |
| 存量代码 | ★★★ | ★★★★ |
| 领域知识 | ★ | ★★★★★ |
| 架构决策 | ★★ | ★★★★★ |
| 团队隐性经验 | ☆ | ★★★★ |

**核心洞察**：AI 编码工具会越来越同质化，团队之间的差距在于积累了多少高质量的、结构化的领域知识。

## 容易被忽略的代价

### 心流中断

传统编码是「想→写→想→写」的连续流，AI 编码变成了「想→写 Spec→等→审→改→想」的间歇流。

### 上下文的隐性成本

更大的隐性成本是上下文管理本身：你需要有意识地决定给 AI 看什么、不看什么。

### 现在不是终态

编程可能是 AI 产生飞轮效应最直接的领域 —— AI 辅助编码 → 效率提升 → 更多代码产出 → AI 能力增强 → 更好地辅助编码。

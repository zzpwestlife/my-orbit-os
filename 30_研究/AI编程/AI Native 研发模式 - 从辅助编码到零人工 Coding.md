# AI Native 研发模式：从辅助编码到零人工 Coding

## 核心理念

> 把 AI 当打字员用，天花板很低。把 AI 当施工队用，才有真正的效率革命。

**目标**：不再让 AI 当"打字员"，而是让它当"施工队长"。

## 辅助编码的四大痛点

| 痛点 | 具体表现 | 根因 |
|------|----------|------|
| **人机协作无标准** | 效果完全取决于个人"提示词"功力 | 没有统一的 AI 交互规范 |
| **流程断点** | 工程师变成"人肉翻译器"，在方案文档和 IDE 之间来回搬运 | 设计工具和编码工具之间数据隔离 |
| **上下文缺失** | AI 不认识你的项目，可能重复造轮子、违反架构规范 | AI 无法主动读取项目代码库和技术规范 |
| **文档脱节** | 方案写进 Wiki 就再没更新过 | 文档和代码不在同一个版本控制系统里 |

**核心矛盾**：人与 AI 的交互缺乏规范，导致输出质量不可控。

## OpenSpec + CodeBuddy 全链路方案

### 什么是 OpenSpec？

OpenSpec 是一套机器和人都能理解的"研发契约"。

**比喻**：
- **以前的做法**：你像个包工头，脑子里装着模糊的房子样子，跑到砖厂喊"来 100 块砖"
- **OpenSpec 的做法**：你的核心工作是和 AI 一起**把建筑图纸画清楚**，AI 施工队根据这份**唯一的、标准的图纸**全自动施工

### 目标态：人做什么，AI 做什么？

| 阶段 | AI 负责 | 人负责 |
|------|---------|--------|
| 需求分析 | 提炼需求、发现遗漏、结构化输出需求文档 | 优先级判断，审批需求边界 |
| 方案设计 | 生成技术方案、架构图、接口定义、风险清单 | 技术选型拍板，安全审查 |
| 代码开发 | 根据设计方案进行多文件编码、补充注释和单测 | 评审关键代码，控制合并门禁 |
| 测试验证 | 生成测试脚本、执行回归测试、分析失败原因 | 审核高风险场景，最终放行决策 |
| 发布上线 | 校验实现是否与需求一致，提供发布清单 | 审批发布窗口，处理事故升级 |

**人的核心角色只有三个：决策、审批、把关。**

## 核心工作流：三步走

### Step 1：/opsx:propose — 先想清楚，再动手

> **原则：严禁直接让 AI 写大段业务代码，必须先生成规划文档。**

AI 会自动在 `openspec/changes/[变更名]/` 目录下生成：

| 文件 | 作用 | 通俗理解 |
|------|------|----------|
| `proposal.md` | 需求背景与目标 | "为什么做"和"做什么" |
| `design.md` | 技术方案与架构决策 | "怎么做" |
| `tasks.md` | 带复选框的实施清单 | AI 的"施工单" |
| `specs/` | 规范增量 | 本次变更的"差异记录" |

**为什么这一步至关重要？** 因为这些文件就是 AI 编码时的**全部上下文**。你在这里多花 10 分钟审查，编码阶段能省 2 小时的返工。

### Step 2：/opsx:apply — 让 AI 按图施工

AI 会：
- 读取 `tasks.md` 中的清单
- 结合 `design.md` 和 `proposal.md` 的完整上下文
- 跨文件批量生成/修改代码
- 每完成一项自动在 `tasks.md` 里打钩 ✓

**开发者此时只需要做一件事：Code Review。**

### Step 3：/opsx:archive — 让规范活起来

MR 通过后执行，系统自动将本次规范增量合并到 `openspec/specs` 主目录，清空变更草稿。

**这意味着什么？** 你的项目文档永远和代码保持同步。没有"僵尸 Wiki"，没有"代码才是文档"的无奈。

## 完整六步工作流

1. **Explore**：与 AI 讨论需求，沉淀文档（不写代码）
2. **Propose**：生成完整规划文档 → **Review 卡点**
3. **Apply**：AI 按 tasks.md 自动编码
4. **Verify**：AI 代码审计，比对 design.md
5. **MR Review**：人工审查 + 合并
6. **Archive**：规范增量合并到主干

**关键卡点**：Step 2 的 Review 是质量的生命线。`tasks.md` 建议控制在 **15 项以内**。

## 让 AI "懂" 你的项目：三大武器库

```
知识库 → 让 AI "知道"我们的项目
MCP   → 让 AI "连接"我们的工具
Skills → 让 AI "掌握"我们的方法
```

### 知识库：AI 的项目记忆

**通道一：OpenSpec specs/**（核心记忆）
- 项目的"活文档"
- AI 执行 `/opsx:apply` 时会自动读取
- 每次 `/opsx:archive` 后自动更新，**始终与代码保持同步**

**通道二：MCP 外部知识**（辅助记忆）
- 业务术语表、架构决策历史、踩坑记录等

### MCP：AI 的工具连接层

让 AI 能直接访问团队的内部工具，消除"复制粘贴"式的跨工具搬运。

| MCP 工具 | 连接目标 | AI 获得的能力 |
|----------|----------|---------------|
| TCS Component | 前端组件库 | 查询组件使用规则 |
| TAPD MCP | TAPD 需求平台 | 直接查询原始需求/Bug 单 |
| iWiki MCP | 文档平台 | 直接检索设计文档、架构文档 |
| 极光流水线 MCP | 部署平台 | 触发构建、查看部署状态 |

### Skills：AI 的专业技能包

Skills 是团队沉淀的标准化操作流程（SOP），封装成 AI 可复用的"技能包"。

## openspec-installer：一个生产级 Skill 的完整构造

### 解决什么问题？

把新人入职"搭环境"的 8 步（至少 1 小时）压缩成一句话：

```
curl -fsSL http://内部skill命令
```

### 文件结构

```
openspec-installer/
├── SKILL.md                          # 600+ 行的完整安装 SOP
├── version.json                      # 版本控制元数据
├── scripts/
│   ├── INSTALL_MAC_LINUX.sh          # macOS/Linux 环境自动安装
│   ├── INSTALL_WINDOWS.ps1           # Windows 环境自动安装
│   ├── install_skills.sh             # 项目 Skills 批量安装
│   ├── check-skill-updates.sh        # 所有 Skills 版本检测
│   └── self_update.sh                # Skill 自身热更新
└── templates/
    ├── mcp-servers.json              # MCP 配置模板
    ├── skill-bundle.json             # 项目默认 Skill 套装清单
    └── openspec-config-awareness.md  # Bridge Rule 模板
```

### 三个关键设计决策

#### 决策一：Bridge Rule — 解决"链路断裂"问题

OpenSpec 的 `config.yaml` 支持自定义 rules 字段，但 **AI 不知道要去读这个文件**。

**解决方案**：在安装时自动生成一个 Bridge Rule 文件，告诉 AI：
> "当你执行 OpenSpec 操作时，先去读 `openspec/config.yaml` 中的 rules。"

使用 `alwaysApply: true`（每次会话自动加载），context 开销可忽略不计。

#### 决策二：Token 交互 — 在 SKILL.md 指令层完成

MCP 服务需要 PAT Token 才能认证。CodeBuddy 的 bash 执行环境是**非 TTY 的**，`read -p` 会导致脚本挂起。

**解法**：把 Token 交互写在 SKILL.md 的 SOP 里，让 AI 在对话中完成。

**同时**，在 Token 交互之前，自动将 `.mcp.json` 加入 `.gitignore`，防止含有 Token 的文件被意外提交。

#### 决策三：版本检查的三级降级策略

1. **优先**：通过工蜂 MCP 服务查询仓库中的 version.json
2. **降级**：如果在仓库目录内，直接读取本地 version.json
3. **兜底**：静默跳过版本检查，不阻塞安装

**核心原则**：辅助功能的失败不应该阻塞核心功能。

## 团队协同实践

### 原子化变更原则

- 一次变更解决一个需求
- tasks.md 控制在 15 项以内
- 小步快跑

### "规范即文档" 原则

`openspec/specs/` 目录就是永远与代码保持一致的"活体文档"，替代传统的沉睡 Wiki。

**禁止绕过 OpenSpec**：否则会破坏"规范与代码"的同步性，Spec 沦为"死文档"。

### MR 审查的双重视角

| 审查维度 | 内容 | 对照文件 |
|----------|------|----------|
| 代码逻辑 | AI 生成的代码是否遵守约束条件 | design.md |
| 架构合规 | 技术方案是否符合团队底线 | proposal.md |
| 需求覆盖 | 所有规范中定义的行为是否已实现 | specs/ |

## 核心洞察

**AI 不是来替代程序员的，而是来重新定义"程序员"这个角色的。**

以前，我们的核心价值是"能写代码"。现在，我们的核心价值是"能指挥 AI 写出正确的代码"。

这像极了软件工程发展史上的一次次跃迁：
- 从机器码到汇编：我们不再关心寄存器
- 从汇编到高级语言：我们不再关心内存地址
- 从写代码到 AI Native：**我们不再关心具体的代码实现，而是关心需求定义和架构决策**

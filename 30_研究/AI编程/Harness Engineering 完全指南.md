# Harness Engineering 完全指南

## 核心定义

**Harness Engineering** 是为强大但方向不定的 AI Agent 套上"缰绳"的工程体系，通过**约束、引导并纠正其行为**，确保它能沿着预设轨道稳定、可靠地前行。

> AI Agent = SOTA 模型（野马）+ Harness（驾驭系统）= 千里马

Harness 是：除了 LLM 本身之外，让 Agent 真正能干活的一切**基础设施**。它不是"更好的 Prompt"，而是**优化模型运行所需的环境、机制与基础设施的总和**。

## 为什么需要 Harness Engineering

### R.E.S.T 模型：四个核心目标

| 目标 | 定义 | 关键要求 |
|------|------|----------|
| **可靠性** (Reliability) | 持续稳定提供服务 | 失败可恢复、操作幂等性、行为一致性 |
| **效率** (Efficiency) | 资源使用有效性 | 资源可控、低延迟响应、高吞吐量 |
| **安全性** (Security) | 保护系统免受破坏 | 最小权限、沙盒执行、输入/输出过滤 |
| **可观测性** (Traceability) | 理解内部状态与决策 | 全链路追踪、决策可解释、状态可审计 |

### Agent-First 时代的必然要求

- **工程复杂性持续攀升**：从贪吃蛇到百万行代码级别的复杂产品
- **角色跃迁**：从"执行者"到"设计者"——人类成为架构师，AI 成为生产力
- **硬约束需求**：仅靠 Prompt 的"软约束"远远不够

## Anthropic 的三大新模式（2026）

Anthropic 第二课的核心问题：**What can I stop doing?**（你的 Harness 里有多少东西可以扔掉了？）

### 1. 用 Claude 已经会的东西

- Claude 3.5 Sonnet 在 SWE-bench 上拿 49%，只靠 **bash + text editor**
- 不是给 Claude 造新工具，而是让它用已经会的工具**自己组合出解法**
- Agent Skills、Programmatic Tool Calling、Memory Tool 都是 bash + text editor 的组合

### 2. 让模型自己编排

传统假设：每次工具调用结果都要回到上下文窗口。但这常常是浪费。

**新思路**：给 Claude 代码执行工具（bash/REPL），让它自己写代码来调用工具、过滤结果、串联逻辑。只有最终输出回到上下文窗口。

- **编排权从 Harness 转移到模型**
- BrowseComp 测试：准确率从 45.3% → 61.6%

### 3. 让模型自己管上下文与记忆

**Skills**：每个 skill 的 YAML frontmatter 是简短描述，完整内容按需通过 read file 展开。

**Context editing**：选择性删除已过时的上下文。

**Subagent**：让 Claude 知道何时应该分叉干净的上下文窗口。

**Memory folder**：给 Claude 一个可读写的文件夹，让它自己决定持久化什么。
- Sonnet 4.5 + memory folder：BrowseComp-Plus 从 60.4% → 67.2%
- Opus 4.6 的记忆进化：从"记下 NPC 说了什么"到"记下自己哪里打输了"

## Harness 的组成部分

### PPAF 闭环

Agent 的核心运行机制：**感知（Perception）→ 规划（Planning）→ 行动（Action）→ 反思（Feedback/Reflection）**

### 顶层抽象：带边界控制的 REPL 容器

- **Read（读取）**：上下文管理器将外部世界翻译成结构化 Prompt
- **Eval（评估/执行）**：调用拦截器捕获意图并路由到工具执行器
- **Print（打印/反馈）**：反馈汇编器组装观测结果重新注入上下文
- **Loop（循环）**：持续循环直到达到目标或触发终止条件

### 底层转换机制

**核心挑战**：在"无限"的外部世界状态与"有限"的 LLM 上下文 Token 之间建立双向映射。

**Token 转化流水线**：
1. 信息源收集
2. 相关性排序
3. 压缩与摘要
4. 预算分配
5. 模板组装

**关键思想**：把注意力管理变成外部工程问题，而非指望模型"自己想清楚"。

## 核心设计原则

1. **为失败而设计**：将异常视为常态，具备容错、重试和优雅降级能力
2. **契约优先**：所有交互由明确的契约（Schema、API、Event）定义
3. **默认安全**：最小权限、零信任、纵深防御
4. **决策与执行分离**：规划与执行在逻辑和物理上解耦
5. **万物皆可度量**：每个行为、决策、资源消耗都可度量
6. **数据驱动进化**：建立从数据采集到模型/知识更新的闭环

## 系统架构

### 控制平面 vs 数据平面

- **控制平面**：决定做什么（任务调度、资源配额、行为规划、策略与权限）
- **数据平面**：如何去做（Agent 运行实例、状态存储、记忆存储、沙盒执行环境）

### 四个功能层级

1. **接入层**：API Gateway、认证授权、流量控制
2. **编排层**：任务调度、工作流引擎、状态机
3. **执行层**：Agent 运行时、工具执行器、沙盒环境
4. **存储层**：上下文存储、记忆管理、日志与追踪

## 关键工程实践

### Function Calling 生命周期

1. **Schema 序列化**：工具列表及参数定义注入 Prompt
2. **触发生成**：LLM 生成包含工具名称和参数的文本
3. **确定性反序列化**：Harness 捕获并反序列化（最脆弱环节）
4. **观测注入**：执行结果封装成观测文本重新注入

**降级路径**：
- 反序列化失败 → 重试或回退到文本
- 执行失败 → 交互式补充或反思重规划

### 沙盒执行框架

- **Level 1**：进程级隔离（chroot/namespaces）
- **Level 2**：容器级隔离（Docker）—— 推荐默认
- **Level 3**：轻量级虚拟机（Firecracker）—— 不可信代码
- **Level 4**：完整虚拟机（KVM/QEMU）—— 极少数特殊任务

### 资源管理

- 预算与配额（Token、API 调用、CPU 时间）
- 超时控制
- 重试策略（带退避）
- 熔断机制
- 优雅降级

### 策略门控（Policy Gateway）

位于"规划器 → 执行层"之间的最后安全检查：
- 权限检查（RBAC/ABAC）
- 敏感数据过滤（PII/密钥检测与脱敏）
- 指令注入防御
- 审计日志

## 该加的还是得加

### 缓存设计五原则

1. 把动态内容放在提示词最后
2. 有新消息直接追加 messages，不要改 prompt
3. 不要在会话中随便切换模型
4. 谨慎管理工具（添加/删除会让缓存失效）
5. 对 agents 把 breakpoint 移到最新消息

### 声明式工具做边界

把需要**安全管控、用户交互或审计追踪**的动作从 bash 提出来，做成独立工具。

**判断标准**：**可逆性** —— 越难撤销的操作，越值得做成独立工具。

例如：[[Claude Code]] 的 `edit` 工具是独立工具，可以做 staleness check，避免覆盖。

## 度量指标

- **任务效能**：成功率、指令遵循度、工具使用有效性
- **服务质量**：端到端延迟、首次响应延迟、错误率
- **资源效率**：平均 Token 消耗、平均工具调用次数
- **安全与合规**：策略拒绝率、安全事件数

## 核心洞察

**持续重新评估**：Harness 的每一个组件都要定期问一遍：**"这个，模型自己能做了吗？"** 能做了，就扔掉。

Harness 的可能性空间不会随模型进步而缩小，它只是在不断变化。

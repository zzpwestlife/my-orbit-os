# AI Agent 上下文控制实战

## 核心洞察

> AI Agent 架构设计中，所有问题最终都归结为一个点：**上下文里的注意力分布**。

开发 AI Agent 遇到的三类典型问题——步骤被跳过、规则失效、输出同质化——本质上指向同一底层原因：LLM 对上下文不同位置的信息注意力是非均匀分布的。

## 架构演进路径

### 第一阶段：Plan & Execute 陷阱

从教科书照搬"主 Agent 编排 + 子 Agent 执行"的三层架构，常见问题：
- **小改动成本过高**：任何修改都要走完整流程
- **主 Agent 越权**：提示词约束无效，主 Agent 自己动手修代码
- **Plan & Execute 的误解**：这是工作方式，不是架构约束。没有人规定必须切割出 Planner 和 Executor 两个独立组件。

### 第二阶段：[[Skill注入]] 替代冗余 Sub-Agent

将子 Agent 的 System Prompt 转换为 **[[Skill]]**，直接注入主 Agent 上下文，而非新起子进程：

- 性能不降甚至提升（复杂任务）
- Token 开销减少：砍掉通信链路成本
- 天然继承上下文：无需设计"如何把信息传给子 Agent"

> 关键结论：Sub-Agent 消失并非因为 Skill 很厉害，而是暴露了原来的 Sub-Agent 设计本身是冗余的。

### 第三阶段：[[Task Reiteration]] 解决长任务稳定性

To-Do List 的真正价值不是"记录"，而是持续执行**任务重申**：

- 每步完成后把下一步任务推到上下文最末端
- 不断刷新模型的注意力焦点
- 静态放在开头的 To-Do List = 无效

#### 两类信息的处理原则

| 信息类型 | 特征 | 存放位置 |
|----------|------|----------|
| **静态规则** | 全局通用、不变 | System Prompt（始终可见，利用 KV 缓存） |
| **动态信息** | 计划/进度/当前 Skill | 上下文尾端（每步重申） |

> ⚠️ 修改 System Prompt 哪怕一个字，会导致之后所有 KV 缓存失效，代价极高。

### 第四阶段：上下文隔离——重新引入 Sub-Agent

当问题从"该看到的没看到"变成"**不该看到的被看到了**"（输出同质化），需要为局部任务提供干净的上下文窗口：

- **新 Sub-Agent 的本质**：上下文隔离，而非架构分层
- 只注入该任务需要的信息，屏蔽已生成的结果（避免模仿）
- 与 Reiteration 结合：精确控制子 Agent 看到什么、不看到什么

## 注意力分布规律

```
注意力强度：
┌────────────────────────────────────────────────────────────┐
│ System Prompt (高)        ...中间内容 (低)...    末尾 (高)  │
└────────────────────────────────────────────────────────────┘
```

**现象解释：**
- 规则失效 → 规则被大量中间内容"埋没"，模型没忘，只是不优先关注了
- 赶工现象 → 上下文接近上限时，模型有压缩输出的训练倾向（"上下文焦虑"）

## 对新概念的正确态度

> 不要因为某个热门项目用了某个框架就照搬。追问：**它为什么存在？它解决的是什么问题？我的系统真的需要这个吗？**

新名词（Skill、Harness、Task Reiteration）本身不重要。重要的是识别你的系统到底在哪个维度出了问题，然后针对性选择工具。

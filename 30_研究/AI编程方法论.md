# AI 编程方法论

## 核心洞察

### 1. 认知门槛 > 技术门槛

**问题本质：** 不是 AI 不够强，而是人不知道该告诉 AI 什么。

> "用 AI 写代码，真正卡住你的不是技术，是翻译层。"

**三个层次的门槛：**
- **技术门槛**：已被 AI 压得很低
- **认知门槛**：如何将模糊想法转化为清晰需求
- **翻译门槛**：如何用 AI 能理解的方式表达需求

**解决方案：**
- dev-planner-skill：通过对话式选择题收集需求
- 五阶段流程：对话收集 → 生成文档 → 检测工具链 → Agent 团队开发 → 交付报告

---

### 2. 上下文质量决定 AI 上限

**Naval 的核心观点：**
> "英语是最热门的新编程语言。不要去学那些 AI 的技巧和窍门，因为这些东西的寿命是以周来计算的。"

**关键认知：**
- AI 适应你的速度 > 你适应 AI 的速度
- Token 不是 AI 的氧气，你的 Markdown 文件才是
- 上下文越薄，AI 能做的事就越浅

**Obsidian + Claude Code 的价值：**
- 笔记库 = AI 的"完美记忆"
- 双向链接 = 知识网络
- 持续写作 = 构建数字镜像

**实践案例：**
- `/trace` 命令：追踪与工具的关系演化史
- `/connect` 命令：跨域连接，发现隐藏模式
- `/challenge` 命令：用历史笔记质疑当前观点
- `/ideas` 命令：30 天笔记扫描 + 跨领域模式检测

### 3. 文件系统即数据库

**Personal Brain OS 架构：**

```
核心原则：No database, No API keys, No build step
只需要：80+ Markdown/YAML/JSONL 文件
```

**三层渐进式披露：**
1. **Level 1 - 路由层**：轻量级路由文件（SKILL.md）
2. **Level 2 - 模块层**：模块特定指令（CONTENT.md, OPERATIONS.md）
3. **Level 3 - 数据层**：实际数据（JSONL logs, YAML configs）

**格式选择的智慧：**
- **JSONL**：append-only，流式友好，防止数据覆盖
- **YAML**：层级清晰，支持注释，人机可读
- **Markdown**：LLM 原生支持，通用渲染

**关键设计：**
- 模块隔离加载，避免上下文污染
- 跨模块引用，构建知识图谱
- Git 版本控制，零依赖可移植

### 4. MCP 工具设计原则

**核心理念：Agent 工具是 AI 的用户界面**

**Agent 如何"看"工具：**
```
工具 = (名称, 描述, 参数 Schema)
```

**设计原则：**

#### 命名
- ✅ 动词优先：`create_github_issue`
- ✅ 完整自解释：`slack_send_message`
- ❌ 依赖隐含上下文：`send_message`

#### 描述
回答四个问题：
1. What - 这个工具做什么？
2. When - 什么时候使用？
3. Constraints - 有什么限制？
4. Output - 会返回什么？

#### 参数
- 提供具体示例：`"facebook/react"` 而非 `<owner>/<repo>`
- 明确必填/可选
- 说明默认值
- 描述失败情况

**工具数量控制：**
- OpenAI 建议：≤ 20 个工具
- 实践建议：1-5 个精心设计的工具 > 20 个随意堆砌的工具

### 5. 工具选择：OpenClaw vs Claude Code

**OpenClaw 的问题：**
- Token 消耗极高（200 元跑 3 个任务）
- 稳定性差，经常崩溃
- 全自动化不安全（可能生成敏感内容）
- 对普通用户门槛高（需要配置 MCP、Skills、API）

**Claude Code 的优势：**
- 稳定可靠
- 配合 Skills 效率高
- 更适合实际生产工作
- 成本可控

**核心观点：**
> "OpenClaw 虽然易用，但是不实用。OpenClaw 能干的事情，用 Claude Code 也都能干。"

### 6. AI 时代的程序员进化

**7 个等级：**
1. LV1：尝鲜 Copilot 补全
2. LV2：谨慎使用，边用边审视
3. LV3：彻底放飞，全盘接受
4. LV4：命令行召唤 AI
5. LV5：多模型互相审查
6. LV6：随时随地编程
7. LV7：成为 AI 编程布道者

**Naval 的洞察：**
> "AI 不会取代程序员，而是让程序员更容易取代其他所有人。"

**程序员的两大优势：**
1. 能看懂底层（处理 AI 训练数据之外的问题）
2. 能处理抽象漏洞（AI 生成代码的 bug 和架构问题）

**底层知识 = 驾驭 AI 的方向盘**

---

### 7. AI 时代的职业倦怠与边界

**核心矛盾：效率提升 10 倍，疲惫感却更强**

**Steve Yegge 的"吸血鬼效应"：**
- 生产力提升超过 2 倍时，技术开始反向塑造使用者
- "瞌睡攻击"现象：长时间 AI 编程后突然入睡
- 工作产出大幅提升，但疲惫感以更快速度积累

**认知负荷的本质变化：**

```
传统工作模式：
- 一天深度专注于单一问题
- 保持连贯的思维路径

AI 辅助模式：
- 一天并行处理 5-6 个不同问题域
- 每个问题耗时缩短至 1 小时
- 频繁切换构成新的认知负荷
```

**"AI 不会在问题间隙感到累，但我会"**

**工作量蔓延机制（哈佛商业评论研究）：**
1. AI 提升任务完成速度
2. 组织提高交付周期预期
3. 员工更加依赖 AI
4. 任务范围扩张
5. 工作密度和认知负载加剧

**价值分配问题：**

假设 AI 使产出提升 10 倍，9 倍差额价值由谁获得？

- **情景 A（被榨干）**：保持工作时长，全部增量交给雇主
  - 雇主获得 10 倍产出
  - 工程师收入不变，劳动强度显著上升

- **情景 B（理想但不可持续）**：缩减工作时长至 10%
  - 个人获得更多闲暇
  - 组织整体产出落后，长期面临生存风险

**$/小时 公式：**
- 分子（年度薪酬）短期难变
- 分母（实际工时）具有弹性
- AI 放大了分母变化对分子的影响

**认知活动的生理极限：**
- 创意领域持续成就者：每日有效工作时长 ≤ 4 小时
- 剩余时间用于恢复、漫游、输入
- 这不是效率问题，而是生理极限

**能力上限与下限：**
- 上限在扩张：AI 让顶尖工程师产出更高
- 下限在消失：识别和表达自身极限的能力缺失
- "不切实际的美丽标准"：少数人的极限被视为常态

**解决方案：重新定义工作日**

Steve Yegge 的主张：
- AI 时代有效工作日应缩短至 3-4 小时
- AI 自动化执行性任务，保留高阶认知活动
- 高阶认知活动对注意力和情绪资源消耗远高于执行性任务

**关键问题：**
> "当 AI 不断告诉我们'还可以更快'，也许更需要被听见的问题是：还可以更慢吗？"

**实践建议：**
- 识别自己的极限在哪里
- 减少公开活动和会面邀请
- 不追求每一个可见的技术赛道
- 下午合上电脑，与家人散步
- 把刻度盘往回拉

- 分析描述 vs 历史样本
- 降低假阳性和假阴性

## 实践框架

### 知识管理层

**管理笔记库，而非管理 AI**

```
笔记库是根，Prompt 是叶
根深了，叶子自然茂盛
```

**三个关键实践：**
1. **持续写作**：每天一条笔记，反思/想法/学习
2. **双向链接**：用 `[[]]` 连接相关笔记
3. **结构化**：CLAUDE.md 告诉 AI 你是谁、怎么工作、要什么标准

**Voice System：**
- 5 个属性评分（1-10）：Formal/Casual, Serious/Playful, Technical/Simple, Reserved/Expressive, Humble/Confident
- 50+ 禁用词列表（三层级）
- 结构化陷阱清单

---

### 工作流层

**Content Pipeline（7 阶段）：**
1. Idea → `ideas.jsonl`（5 维度评分，≥15 分推进）
2. Research → `knowledge/research/`
3. Outline → 结构化大纲
4. Draft → 初稿
5. Edit → 4 轮编辑（结构/语气/证据/朗读）
6. Publish → `posts.jsonl`
7. Promote → 多平台分发

**Personal CRM：**
- 4 个圈层：inner (周), active (双周), network (月), dormant (季度)
- `can_help_with` + `you_can_help_with` → 自动匹配介绍
- 情感追踪：positive, neutral, needs_attention

**Automation Chains：**
- 周日回顾：metrics_snapshot → stale_contacts → weekly_review
- 内容构思：bookmarks → ideas → content_calendar

---

### 开发层

**dev-planner 五阶段：**
1. **对话收集需求**：选择题 + "让 AI 帮我决定"
2. **生成开发文档**：架构图 + API 文档 + 代码规范
3. **检测工具链**：GitHub/数据库/Docker/网络搜索
4. **Agent 团队开发**：后端/前端/测试/文档工程师并行
5. **交付报告**：项目结构 + 提交历史 + 三版本使用说明

**关键经验：**
- 需求描述越具体，结果越好
- 规划阶段多花时间，开发阶段省麻烦
- 文档是最重要的资产（给未来的你和 AI 看）
- 遇到错误让 AI 自己处理
- 部署可以单独处理

## 核心原则总结

### 1. Context Engineering > Prompt Engineering

从优化单次交互 → 设计信息架构

### 2. 让 AI 适应你，而非你适应 AI

AI 的选择压力是最大限度对你有用

### 3. 管理笔记库，而非管理 AI

笔记库是 AI 理解你的唯一接口

### 4. 底层知识是方向盘

懂原理的人永远能更好地驾驭 AI

### 5. 工具是跳板，不是替代品

AI 释放创造力，而非取代创造力

### 6. 焦虑的解药是行动

去了解 AI 的工作原理，知道该不该害怕它

### 7. 识别你的极限，而非追求无限

效率提升不等于工作时长增加，认知负荷有生理极限
